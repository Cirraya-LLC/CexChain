Bo wrote this text from the contract's source (Bo edition 1). A clause marked with a rule, such as [R3], states what Bo inferred by that rule instead of reading it in the source; the last section explains each rule.

1. Parties
1.1 we: bound to a ledger when an instance is created. [R3]
1.2 customer: bound to a ledger by each allocate, with the consent of the customer. [R3, R23]

2. Each instance
2.1 Each instance is a resource named IP地址.
2.2 地址: a text, given when an instance is created.
2.3 cooling period: 30 days, the same for every instance.
2.4 holder: a party; each instance starts with none, and actions set it. [R20]
2.5 Creating an instance (function create) names the ledgers of the parties bound at creation and sets the fields given at creation. It needs no party's consent: the parties agree through the actions below.

3. States
3.1 An instance starts in the state active. [R4]
3.2 Its states are active, cooling, and allocated.
3.3 No state is final: some action can start from any state.
3.4 Each change of state, the first state included, is recorded as an event.

4. Actions
A call that does not meet one of an action's requirements is refused, and the instance does not change. A missing consent is not a refusal: the call waits for it.

4.1 allocate
  4.1.1 A built-in action of Bo, with the standard terms of Bo's standard library (cexchain bo stdlib show allocate): the clauses marked R19 state them, after the contract's own clauses.
  4.1.2 Started by the home ledger on its own word. [R19]
  4.1.3 It needs the consent of the customer. Each such call names the ledger of the customer and binds the customer to it. [R3, R23]
  4.1.4 If the instance is cooling: [R7, R19]
    4.1.4.1 Requirement 1: the cooling period or more has passed since the instance last changed state. [R19]
  4.1.5 If the instance is active or cooling, it becomes allocated; otherwise the call is refused. [R19]
  4.1.6 It sets the holder to the customer. [R19]
  4.1.7 An AI agent may start it within its delegation. [R14]

4.2 reclaim
  4.2.1 A built-in action of Bo, with the standard terms of Bo's standard library (cexchain bo stdlib show reclaim): the clauses marked R19 state them, after the contract's own clauses.
  4.2.2 Started by us, whose agreement it needs.
  4.2.3 If the instance is allocated, it becomes cooling; otherwise the call is refused. [R19]
  4.2.4 It sets the holder to none. [R19]
  4.2.5 An AI agent may start it within its delegation. [R14]

5. Rules Bo applied
[R3] A role the contract first names as an action's counterparty (after to) is bound to a ledger by that action, with its consent; every other role is bound to a ledger when an instance is created.
[R4] An instance starts in the one state that no state change leads to; if there is none, in the state active.
[R7] A state used as a condition means the instance is in that state.
[R14] An AI agent may start an action within its delegation, unless the action says AI agent can propose; then the agent only proposes, and a person approves.
[R19] A built-in action has the standard terms Bo's standard library gives it (cexchain bo stdlib show ACTION): who starts it, whose consent it needs, the states it starts from and leads to, and what it changes. The contract's own clauses come first and add to them; R8 adds no consent to the standard terms.
[R20] The pledgee and the payee, and a resource's holder, used by an action (the standard terms of a built-in action included) but not declared by the contract, are fields of each instance, holding no party until an action sets them.
[R23] A role that allocate binds is bound again by each allocation, with its consent: a resource goes to one holder at a time, and each allocation names it.
